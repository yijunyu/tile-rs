id: 38
area: lowering
title: bounds check refuses a cube matmul by measuring it against VECTOR limits
opened: 2026-09-16
closed: 2026-09-17

## wanted
tile mm.mlir -t pto --cross ascend -o mm.pto.mlir

for a 128x128x128 f16 matmul whose M/K/N are declared as
`llvm.mlir.constant`, so that mlir_to_pto's tmatmul lowering (loc=left /
loc=right / loc=acc, TMATMUL, TSTORE) is emitted.

## got
exit 1, for every size tried (128, 192, 256, 384, 512, 1024):

  bounds (DAV_2201): UB ok; repeat ok; DMA stride FAIL (arch DAV_2201: row
  stride 32768B exceeds the 16-bit descriptor field's 32767B (C8) ...)
  BOUND: repeat on __tile_matmul_f16 — arch DAV_2201: 16384 elements of 4B is
  256 repeats of an 8-bit field that holds 255 (C7); one instruction reaches
  16320 elements, so chunk it
  tile: the tiling does not fit DAV_2201. Emitting it would produce a kernel
  the hardware cannot run.

Three things are wrong, and the last one matters most:

1. The limits are the VECTOR unit's. A repeat counter and a UB working set do
   not bound a TMATMUL: the cube's operands live in L1/L0A/L0B and its result
   in L0C. `__tile_matmul_f16` should not be measured against C7/C1 at all.
2. The element size is 4B for an f16 matmul. `tile -i` reports
   "dtypes: int32, float16 -> promotes to int32 (4 bytes)", so the f16 operands
   are being sized as int32 -- the i32 SSA handles the tile intrinsics pass
   around are being read as the DATA type.
3. The row stride it computes (32768B for a 128x128 f16 tile, whose real row
   stride is 256B) does not correspond to anything the generated code does.

The refusal is FALSE. The same kernel, generated by omitting the constant
definitions (below), is correct on hardware: rel = 2.206e-07 on 910B, and
20/20 with 0 anti-cheat on 950pr/c310 as GQA's QK^T and P@V
(cannbench-tilers NOTES 270, job_653d01b8afdf).

## workaround
Declare the shape arguments as BARE SSA names with no defining op:

    %t_a = llvm.call @__tile_load_f16(%arg0, %c128, %c128) : ...
    %t_c = llvm.call @__tile_matmul_f16(%c0, %t_a, %t_b, %c128, %c128, %c128)

with no `%c128 = ...` line anywhere. Then `tile -i` says "tile plan: not
computable (no declared extent)", the bounds check has no input and passes,
and the lowering is emitted and is correct.

This is a bad workaround and it costs something real: `parse_u32_from_arg`
chases `llvm.mlir.constant(...)` only, so with the extents hidden
`detect_blocked_matmul_loads` ALSO fails to fire, the operand loads are not
deferred, and the emitter emits a full-shape `loc=vec` tile and tload for each
operand IN ADDITION to the `loc=mat` ones the cube uses. At 128x128 those are
two dead 32KB MTE2 loads (harmless, measured 20/20). At 1024x1024 the dead vec
tile is 2MB and the emit fails outright:

    NPU UB budget (arch a2a3): tile of 2097152B at offset 0B would use
    2097152B > UB_SIZE 262144B (C1)

So today the cube matmul is reachable ONLY at shapes small enough that the
dead vec tile still fits UB, and only by hiding the extents from the bounds
checker -- which is also what stops the K/N-blocked path (the one that
parallelises over N via get_block_idx) from ever being selected.

What would fix it: give the bounds model a notion of WHICH UNIT an op runs on,
so a cube op is checked against L0A/L0B/L0C and L1 capacity and not against
vector repeat counters or UB; and make `parse_u32_from_arg` accept
`arith.constant` as well as `llvm.mlir.constant`, so declared extents stop
being a liability.
