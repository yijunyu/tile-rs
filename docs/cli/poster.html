The tile Swissknife

One command that identifies, profiles, lowers and measures accelerator kernels across 20 representations. Built to a written specification that now runs: 174 of 179 scenarios live under --features pico,stats on this Mac, and nothing is left marked “planned”. The work worth reporting is not the feature list — it is the defects the specification found while being made to pass.

Both feature builds green. That coverage figure carries its configuration on purpose: the default build scores 170/179, because four scenarios need the crypto feature, and setting TILE_SPEC_CROSS/TILE_SPEC_HOSTS scores higher. A number quoted without its configuration is not reproducible. tile backlog reports 3 open, down from eight, and its verdict is healthy — both analysed clusters dissolved as their issues closed. Every op with a reference now agrees on the GPU, including matmul and matvec, which the fixed tolerance could not admit; the run says which is which.

What it does

Convertexact

Pandoc’s grammar for kernels: extension and content magic pick the input form, -t picks the output, a route graph does the rest. Every conversion prints its route and its fidelity class — never only on request.

Runmeasured

-r compiles the emitted kernel, runs it on the real device, and checks it three ways: against our reference, against PyTorch, and the two against each other — because two sources cannot attribute a disagreement.

TuneO4

Sweeps threadgroup widths on the device and records every candidate with its own timing. The artifact gets a header saying which width to dispatch with, on which machine, and that it is one machine’s measurement.

Serve

A loopback view of the same core, with a 19 kB dependency-free wasm bundle that filters the form matrix as you type. Not egui: eframe means a toolchain this tool refuses to acquire silently.

“Identical across three GPUs” was true of one op, not thirteen

That claim came from softmax. Re-running all eleven unary ops on a second GPU: nine agree to the digit, but exp (9.54e-7 vs 4.77e-7) and sigmoid (1.79e-7 vs 5.96e-8) do not. Both far inside tolerance, and the emitted kernel is byte-identical on both machines — so it is the shader library’s transcendentals that differ, not the lowering. Stated because a claim measured on one op should not be carried as a claim about all of them.

Row reductions on Metal covered 32 elements, not the row

reduce_max and absmax used simd_max alone and wrote lane 0’s result. That reduces across one SIMD group — 32 lanes — not the threadgroup, so for any row wider than 32 they returned the maximum of the first 32 elements as the row’s. Measured over a rising 1024-wide row: 0.31 where the true maximum was 10.23.

absmax feeds quantization scales, so a scale from a thirty-second of the row makes everything outside that window saturate on the way to int8 — a model quietly and uniformly wrong rather than obviously broken.

Nothing already built could have caught it. The refusing arm does not fire — there is an arm. The detector does not fire — the output genuinely depends on the intrinsic. And the harness’s own inputs are periodic with period 17, so the maximum always lands inside the first 32 and a correct kernel agrees with this one. It took a hand-written input that rises across the row.

Fixed, and then made catchable: reductions are a shape the harness understands, and the input carries a small ramp so the extreme lands at the end of the row. Rebuilding the pre-fix kernel byte for byte and running it under the new input gives 2.0016 against a true maximum of 2.1019 — under the old input both returned exactly 2.0, which is why it shipped.

The same mistake in three backends

Scanning every backend’s emitted reduce_max for the signature — a subgroup or warp reduce with no barrier and no fold — found it three times. SPIR-V is the worst: if (subgroupElect()) p1[gl_SubgroupID] = val; writes one value per subgroup, scattering eight partial maxima into p1[0..7] where the caller reads p1[row]. The same shape is in rms_norm, which divides by gl_SubgroupSize — normalising over 32 elements and calling that the row.

Backends that do not have it, recorded because an audit that only finds problems is not an audit: linalg and rvv reduce declaratively, aie/bang/gaudi loop over the row, pico carries a barrier, and Metal’s argmax scans serially in one thread.

The same defect in CUDA — refused, not guessed at

Auditing the class turned it up in mlir_to_gpu, where the emitted source says so itself: // block-wide max reduce — warp phase only (assumes N<=32). It declares shared memory for the cross-warp phase and never uses it, and absmax prints cols=1024 into the source it emits — so the width was known and unchecked.

There is no NVIDIA device here. Writing a block reduction nobody can run would be exactly the plausible-looking work this project keeps finding, so the assumption is now enforced instead: a row wider than a warp is refused, naming the width and what it would have returned. --list-ops moved from yes to - for both — the report becoming true, not the backend getting worse.

So the label became a question: how many are like that?

The CUDA bug was documented. It said assumes N<=32 in the source it emitted. That makes it a sample of a class, so all fifteen emitters were scanned for the vocabulary of an unenforced precondition — assumes, only works, must be a multiple, hardcode.

Eleven have none. pto is the disciplined case and the reason this section is not only bad news: it refuses a matmul whose M is not 16-aligned and names the rule — M=30 must be a multiple of 16 (910B2 cube fixedRowSize). Confirmed by calling the emitter directly: M=32 lowers, M=30 refuses.

msl is the gap, and it is a family rather than a kernel: six emitters bake in head_dim 64 or 128, n_embd 4096, n_hc 4, or K % 8 == 0. Two hardcode 64 and two hardcode 128 — per-model specializations, right for the model they were written for and reading at the wrong stride for any other. No crash, no refusal, just wrong numbers.

I filed this as unfixable, and that was wrong. The reasoning was that every one of these is fn emit_…_msl(out: &mut String) — no shape arguments, so nothing to compare against. True of the emitter, false of the problem. The intrinsic carries it: __tile_flash_attn_ext_vec_score_f32(…, dk, dv, ne01, …). The head dimension was passed in and ignored.

So it is a guard, not a ticket. Four kernels now refuse a shape they were not written for, between classification and emission — dk=128 against a kernel specialized to 64 is named and refused instead of silently reading K at half the right stride.

Only a proven mismatch refuses, and the reason is a trap worth naming: the existing resolve_const falls back to a parser that strips the % off an SSA name and returns the digits, so %42 comes back as 42 — a number that looks like a value and is not one. A guard built on that would refuse correct kernels on the strength of an SSA index. The check consults the constant map only; a dynamic shape still lowers, and a test pins that alongside the refusals.

Two remain open because their shape genuinely is not an operand — the pad kernel takes byte strides and no head dimension, and the simdgroup matmul is not declared in tile_std at all. Inferring head_dim from nb11 would work until K is ever f32. Left alone, for the reason the CUDA episode established.

Then the trap turned out to have a second victim

The guard above could not use resolve_const because it turns %42 into 42. That raises a worse question than the one it answered: if a value that is not really known can still become a number, who emits such a number? resolve_const feeds ctx.tile_width, and tile_width sized a threadgroup array.

The reduction kernels declared threadgroup float sdata[local_x] — an emit-time value from the MLIR — while the body writes sdata[tid] for every tid < tcount and reduces from s = tcount/2, where tcount is threads_per_threadgroup: a run-time value the harness picks from the run shape. Two independent sources for one quantity. They agree whenever both come from the same kernel, which is exactly why it survived — the coupling was a coincidence, not an invariant.

Break the coincidence — a kernel emitted for a 64-wide tile, run over a 1024-wide row — and every thread above 63 writes past the end of the array. Measured on the M1 Ultra: max relative error 17.8 against torch, while our own reference and torch agreed to 6.7e-7, so the three-way comparison attributed it to the kernel rather than to a reference.

-O4 made it worse rather than catching it. The sweep runs one compiled source at widths 32…1024, on the argument that the kernels stride by threads_per_threadgroup so a different width is the same arithmetic in a different number of steps — true of the global loop, false of a fixed-size shared array. It measured 1024 as fastest and selected it. Overrunning fastest is still fastest.

Sizing the array by the dispatch ceiling instead of the tile width takes the same case to 6.11e-7, all three agree — and -O4 still picks 1024, at 17.33 µs against 17.50 µs before. The correctness fix cost nothing measurable. idx_data was the same defect a few lines away carrying the argmin half of the same reduction; fixing only sdata would have left it overrunning on exactly the dispatch just made safe. The other four shared arrays were checked and were already guarded.

Nothing about this is Metal-specific, so the other four backends that emit shared memory got the same question. None of them have it, and the reasons are the point: SPIR-V writes layout(local_size_x = N) into the shader and sizes its tile from the same N, so the workgroup size travels with the code; CUDA bakes the width in and states the contract where the person launching it will read it — // Launch: <<<num_tiles, 256>>> above an sdata[8] that is exactly 256/32 warps. Metal was the one with the bug because Metal is the backend where this tool picks the dispatch width — and it picked one the emitted array did not agree with.

The verdict blamed the reference for the kernel’s error

One more step along the same question — what does the harness choose at run time that the kernel fixes at emit time? The grid. The harness dispatches MTLSize(width: grid, height: 1, depth: 1), and seven Metal kernels declare uint2 tgpig and index by both components. Under a 1D dispatch tgpig.y is always 0, so everything above the first row-block of the output is never written.

Running one produced a wrong answer and a false explanation:

kernel vs torchmax rel 1.00e0
kernel vs oursmax rel 1.00e0
ours vs torchmax rel 3.29e-4

“this tool’s own reference disagrees with torch too — the reference is wrong, and the kernel inherited it” — and that is false. The kernel is wrong by 100%. The reference sits 3.29e-4 from torch, which is ordinary f16 accumulation, and it was named as the cause. Anyone reading that line goes and audits the reference.

The function existed to attribute a disagreement and could not see the measurement that attributes it. It took two of the three comparisons and called the both-disagree corner “inheritance”. But inherited claims the kernel matches the reference — the third comparison, computed, printed on the line directly above the verdict, and never passed in. It now takes all three, and says “separate faults” when nothing was inherited.

The 2D grid is now refused rather than dispatched wrongly, naming which side is unable: the kernel is fine, the harness cannot infer the intended decomposition. And that refusal exits 3, not 0 — the old path returned OK because the file had been written, so a CI step reading exit 0 from tile k.mlir -t msl -r would conclude the kernel ran and agreed with torch.

The backlog told me to stop, and it was right

Checking the figure beside this one — three GPUs — I read what the neighbouring fidelity claims assert. design.md defines validated as “checked against a CPU reference on that hardware”; forms.rs carries nine of them, including NVIDIA, TPU v5e, Trainium and Gaudi; and #001 says there is no run harness here for any target but Metal. That class prints on the last line of every conversion.

Filed rather than downgraded: those kernels came from projects that do have the hardware, so the claims may be true and this repo simply carries no evidence. Swapping a possibly-true claim for a definitely-wrong one is not an improvement.

Filing it made the tool say STOP AND RECONSIDER — three open issues in one area, “one design problem wearing three hats”. It was right, and reading them together gives it: the tool reports verification at a granularity its harness cannot deliver — too wide in target, too wide in dtype. The rule that falls out is that a claim about verification names the configuration it was verified in, which is the same rule the drifted coverage figure needed, arriving from a second direction.

Then the stop would not go away. It fires on a count, and an area waiting on hardware nobody here has holds that count forever — and an alarm that cannot be switched off is one people learn to read past, which costs more than the rule earns. The instruction it gives is carried out by writing the cluster document, so that document now stands it down — and only while it accounts for the area: every open id must appear in it. A fourth issue filed outside it brings the stop straight back, which was checked in both directions.

The last op Metal did not lower — and two tests that were not tests

--list-ops had Metal at 17 of 18. The gap was reduce_sum: declared in tile_std, lowered by seven other backends, and refused here rather than emitted as a copy — the refusal even naming what to add. Written in the shape reduce_max had to be rewritten into after the miscompile, and verified on the M1 Ultra at 2.86e-6, all three agree. Metal is now at full marks on the probe’s op list — which is the denominator --list-ops states outright, because a bare “18/18” reads as everything and tile_std declares intrinsics by the couple of hundred.

Saying that out loud raised the next question: was the list the right 18? The probe builds one kernel shape, and 21 declared intrinsics have it — cast_f16 and two kv_cache_update variants were missing for no recorded reason, in a constant named PROBE_UNARY_OPS that already contained argmax and softmax. It is defined by the rule now, all 21. The KV-cache pair turns out to be a gap in eight backends that the report had simply never asked about — --list-ops can only be as honest as its questions. Two more shapes followed, putting max, min, matvec and matmul — the headline op — into a report that had never asked about any of them. 25 ops now, and matmul turns out to lower everywhere except Metal, which implements the f16 and simdgroup variants only.

The next shape was declined, on purpose. The most common signature in the whole intrinsic set is none of the three — 26 ops take (src, dst, ne0, nb_src, nb_dst), the DS4 _scalar family, which appears 61 times in the Metal emitter and zero times in every other one. Probing them would add twenty-six rows reading yes under one backend and a dash under ten, sinking every other backend’s score for failing to implement one backend’s model kernels. So the report now states where its scope ends, rather than leaving an omission for someone to helpfully “complete”.

Then the part that matters: the wrong version was checked to be catchable. Emitting simd_sum with a lane-0 store — the miscompile this op could have shipped — gives 4.96 and “the KERNEL disagrees with torch”, naming the kernel rather than the reference, which is the attribution fix above working on a live case.

Two tests turned out to assert nothing. test_msl_reduce_max checked only that the output contains simd_max — and the kernel that shipped the miscompile contained simd_max too. And my own cluster test read the real backlog through a path that honours an environment variable another test sets under a lock mine did not take: it passed on one feature build and failed on the other by scheduling alone. The decision is now split so the test supplies its own lookup and touches no global state.

Four defects, one shape: a number restated beside the thing that knows it

The coverage figure said 175 of 178 when the suite computed 174 of 179. The band said 15 ops verified when 15 was how many references exist and 14 had been checked. The -r hint promised the harness knew thirteen operations when its table held sixteen. Each was written as prose next to the structure that already knew the answer, and each drifted away from it silently.

Once that was three, it was a signature worth searching for rather than tripping over a fourth time. The search found one: the crate doc opens “tile-rs reads 3 forms and writes 18” — the table holds 20, and --list-forms counts them. Two files away sits the comment “Counted, never written down: a hardcoded ‘reads 2, writes 18’ drifted”. Somebody learned this exact lesson in that file, and the sentence in the next one kept the stale number anyway.

The rest of the sweep came back clean, which an audit has to report as carefully as its finds: the overloaded-extension counts, the eight on-hardware backends, the fifteen emitters and the whole --list-forms footer all check out. One of them only looked wrong until the counting method was fixed rather than the document — the doc was right and the method was not.

Metal lowered max and refused min

Nothing about that was deliberate — the arm is three lines and had never been written. It was invisible until the probe learned to call two-input ops, one commit earlier.

Writing it was the small half. Neither max nor min had a reference, so lowering was all anyone could say about either. Every shape in the harness declares how many input buffers it needs, and every elementwise one declared exactly one — so Shape::Rows2 is the missing member of that family, a variant rather than a flag because the buffer count is what the ABI check compares against the kernel.

Each arm the compiler then demanded turned out to be a real decision. The timing path needed its own loop: the generic one calls a function that takes one row, so a two-input op reaching it panicked rather than quietly timing a different computation — which is the argument for exhaustive matching in one line. Verified on the M1 Ultra: min exact against torch, max at 9.31e-10, all three agree.

The reference cannot pass its own tolerance

Metal refused __tile_matmul_f32 while lowering the f16 variants — the headline gap the matmul-shaped probe exposed. Writing the arm was easy. Running it said something none of the other ops had:

kernel vs torch1.14e-52.72e-4 rel
kernel vs ours1.14e-53.55e-4 rel
ours vs torch9.54e-63.29e-4 rel

Our own reference fails the gate. The tolerance is 1e-5 absolute and 1e-4 relative; the reference sits outside it against torch on a K=64 product, computing the same thing in a different summation order. So no matmul can pass, however correct the kernel — which is why matmul was never in the verified list, and never going to get there by writing a better kernel.

Not closed by widening the number: that is fitting the gate to the sample, and it was rejected once already for f16. What changed is the sentence. The verdict used to end “they are separate faults” — an overreach in the opposite direction from the “inherited” claim it replaced, because here there are no faults at all, only summation order, and all three magnitudes are the same size. It now points at those magnitudes and names both readings, which is the distinction the earlier findings actually turned on: 17.8 against 6.7e-7 was a defect; 1.14e-5 against 9.54e-6 is arithmetic.

The reworded verdict caught a bug I wrote ten minutes later

matvec was the last op Metal did not lower. The first run of it was wrong by 1.74e2 while the two references agreed with each other to 3.05e-5 — one magnitude seven orders above the others, which is exactly the reading the verdict had just been reworded to name.

The cause deserves the space. Shape::scalar binds a kernel’s scalars by name, and carried this pair:

(RowReduce { cols }, "num_elements")=> cols
(_, "num_elements")=> self.out_size()

with a comment on the first line explaining that a reduction must bind this to the row width, because out_size “would make the kernel read rows elements of a rows * cols row and reduce a sliver”. Matvec is a reduction. Its out_size is rows. The new shape fell into the catch-all and summed 4 terms of 256 — the failure the comment describes, one shape before it happened. The _ arm is gone: every shape now says what its kernels loop over.

Metal is 25 of 25. Which broke the refusal guard for the third time — it had asserted Metal refuses matmul_f32, then matvec_f32, and both were implemented within the hour. A test of the refusing default arm should not be a hostage to coverage progress, and each time its gap got filled the easy move was to delete it. It now uses __tile_frobnicate_f32 — a name nothing declares and nobody can implement out from under it.

The backlog lost one of its own issues, silently, for a day

Freezing a reduction kernel as a golden had an effect that has nothing to do with diffs: nine kernels, for backends nobody here can run, became readable, because they were sitting in the tree as files. Reading them found bang’s row reductions copying per_task * sizeof(float) out of a nram_1[1] — a 1024-byte read from a 4-byte buffer — and writing a row’s worth of values where a reduction produces one. Filed, not fixed: there is no Cambricon hardware here, and this repo has twice rejected writing a kernel nobody can run. Fixed a day later without acquiring anything — see the last finding on this page.

Filing it exposed something worse. The listing showed 14 issue files on disk and “6 open, 7 closed”. Thirteen accounted for; nothing said about the fourteenth. An issue filed with an updated: line — a field the parser rejects on purpose — had been dropped by if let Ok(i) = Issue::parse(&t) without a word, and had been invisible since the day before.

A backlog exists so that a known gap is not lost, and its loader was losing one. The strictness is right and stays; enforcing it where nobody can see the result is what was wrong. The loader now returns what it could not read alongside what it could, and the command prints that first — above the counts that do not include it.

The check I recommended does not work, and I ran it wrong as well

Finishing the golden read, gaudi’s reduction turned out to reuse the elementwise loop template: it stores inside the loop and carries no accumulator across iterations, so each pass writes one vector’s sum at its own index. A row reduction produces one value per row. Whether that is wrong depends on how the index space is configured — which is not in the emitted file and is recorded nowhere in the repo — so it is filed as a question, not a defect.

I first filed it as proven, on two claims that were both false. That the files were byte-identical at two row widths: they are not, they differ in a comment. And a cheap rule worth stealing — emit a reduction at two widths and diff — which is not valid at all. msl and tpu ARE identical at both widths and both are correct: one reads num_elements at dispatch, the other takes its shape from the input array at run time. Width-independent text is the right answer for a kernel that gets its width at run time, and the diff cannot tell that from a baked-in constant.

And the comparison itself was run with rtk proxy diff — where diff is one of the wrapper’s own subcommands rather than the diff program. It printed nothing and exited 0 on every pair, including linalg, whose two outputs differ in plain sight. A check that passes everything is not evidence, and the uniformity should have been the tell before the conclusion was. What survives is the question rather than the test: where does this kernel get the extent it reduces over? That is read from the emitter, not from a diff of its output.

Sixteen kernels read, one defect, no hardware

Freezing emitted text turned out to be worth more for reading than for diffing. Softmax is frozen for sixteen backends and carries a max-reduce and a sum-reduce — where the miscompile this repo already shipped once lived — so all sixteen were read.

The question is not whether the text changes with the row width; that check was withdrawn. It is where the kernel gets the extent it reduces over, and fifteen give an honest answer. They name the operation (linalg.reduce, nisa.tensor_reduce, pto.trowsum, softmax_tile, a pico vsum), or take the extent at run time (num_elements at dispatch, x0.shape, an int n parameter), or derive their own sizes from it — CUDA and musa being the model:

cols=1024<<<n, 1024>>>sdata[32]tid < 32
cols=256<<<n, 256>>>sdata[8]tid < 8

Three interdependent numbers, all tracking. Nobody has to trust that kernel — you can read whether it tracks.

SPIR-V answers none of the three. local_size_x = 256 and sdata[8] at both widths, a per-workgroup reduction, indexed by gl_GlobalInvocationID — so a 1024-wide row is four workgroups each normalising its own 256 elements. Correct at 256 by accident of the width somebody tested; wrong above it; and the frozen golden is the 1024 case. Thirteen of these backends have no hardware here, and none of this needed any.

The SPIR-V softmax was filed as unfixable here for want of a Vulkan device. Nobody had checked. This machine has glslangValidator, spirv-val, the Vulkan loader and Mesa’s Vulkan-on-Metal driver — Apple M1 Ultra, KosmicKrisp 26.2.0, Vulkan 1.4.354.

The backlog paid for the assumption. “No run harness for any target but Metal” was never tested, and is now true only of CUDA, Cambricon and Gaudi.

SPIR-V is a backend the tool can measure now, not just emit

Finding a Vulkan device made the throwaway harness worth keeping. assets/harness/vulkan.c satisfies the same contract the Metal one does — device, threadgroup, warmup, per-iteration timings, the values, and the control arm whose whole job is to disagree — so one output format is parsed whichever device was driven.

Three things stopped being Metal-shaped. The ABI parser dispatches by form, because binding a Metal signature’s buffer order onto a GLSL shader is how a harness compares two unrelated numbers. Each path names the tools it needs, and a missing one is reported by name rather than surfacing as an exec error — “the run did not happen” must not read as “the run disagreed”. And the dispatch width: Metal takes its threadgroup at dispatch so -O4 may sweep it, while SPIR-V compiles local_size_x into the module, so the shader’s width wins.

Every SPIR-V op with a reference now runs on the device — exp, log, rsqrt, sigmoid, silu, softmax: all three agree. relu, sqrt and tanh refuse, which is honest rather than a failure.

A message went false along the way and was caught: -t spirv printed “the result cannot be run or measured here” and then measured it. The check compared family names, and vulkan against apple-gpu looks disjoint until Mesa’s driver puts them on one device. It asks about the harness now, which is what the claim was ever about.

“No device here” was the premise of three refusals

SPIR-V’s reduce_max and absmax refused any row wider than 32, and the source said why: they wrote p1[gl_SubgroupID] = subgroupMax(v) — one value per subgroup into an output the caller indexes by row — and “there is no Vulkan device here either, so the same rule: refuse rather than write a reduction nobody can run.”

The reasoning was sound and the premise was false. Both are rewritten in the shape Metal’s reduction uses and both checked on the device over a 256-wide row: all three agree. SPIR-V goes from 11 of 25 to 13 on the probe, and from six verified ops to eight.

RmsNorm was left refusing because it had no reference in the harness — which is a reason to add the reference, not to leave the kernel wrong, so both were done. Its one line held two errors: inversesqrt(sum_sq / float(gl_SubgroupSize) + 1e-6) with subgroupAdd above it, so the sum covered a subgroup and so did the divisor. A 256-wide row got eight different scales, each from a different 32 of its elements. On the device: old 7.94e-2, new 5.78e-7.

And then eps itself. The intrinsic declares an operand; the emitter hardcoded 1e-6 and ignored it — and so did the reference, and so did the torch expression. Three constants agreeing with each other is not a check: change the kernel’s eps and the comparison would have gone on passing. All three read it from the source now, and a non-constant eps is refused rather than defaulted, because a default is a silent change to what the kernel computes.

Verified at three values — 1e-3, 1e-6, 5e-2 — because one value cannot tell “uses eps” from “happens to match”. And the three-way comparison caught the change while it was half done, twice: first the torch expression still said 1e-6, then a blanket replace had left a literal in the reference too. Neither was visible in the diff; both were visible in the run.

Two things had been hiding behind the refusal. The kernels emitted subgroupMax without requesting the extension that provides it, so glslang rejected the shader outright — invisible while they never reached the compiler. A NaN could hide a wrong answer in all five gates

kernel NaN, reference 0.5  →  worst = 0  →  caught = false

A NaN distance is now hoisted to infinity so the disagreement survives, checked in both directions and for infinities. Nothing was falling through it: all five stay green. The same operation, two lowerings, opposite operands

The f16 sweep found __tile_matvec_f16 reading its operands the other way round from __tile_matvec_f32:

f32:  acc += (float)p0[base + i] * (float)p1[i];   ← p0 is the matrix
f16:  sum += p0[i] * float(p1[base + i]);          ← p0 is the vector

Driven through the harness’s ABI the f16 kernel reads buffer 1 at offsets up to (rows-1)×cols while that buffer holds cols elements — out of bounds — and returned a max relative error of exactly 1.0, which is what “returned zero” looks like.

It is a decision, not a typo: the emitter declares that kernel activation(f32), weight(f16), output(f32), a DS4 convention. Choosing the intrinsic’s order over DS4’s may break the kernel it was written for, so it is filed, not fixed, and the sweep skips f16 matvec naming the issue. The fix was wrong, and a golden file three backends away said so

A rank-1 argument’s extent cannot be read off its recorded shape, because the two rank-1 roles record the same shape and want opposite answers:

reduction output over a 1x256 tile   shape (1, 256)   extent 1    one value per row
matvec's vector, loaded as 1x256     shape (1, 256)   extent 256  the vector's length

Taking the row count is right for the first and was applied to both — hence the invalid matvec. Taking the element count r * c fixes matvec and breaks the reduction. That is what the first attempt did, and the frozen golden files caught it: linalg/reduce_sum changed, and so did rvv/reduce_sum — a backend the change never touched.

The extent is now recorded by whoever knows the role. This is the second time in one sitting that a first attempt at a fix or a check was wrong and only an independent gate said so. That is the argument for having more than one, and for freezing output you do not expect to change.

The bug that is invisible unless the matrix is rectangular

Seven coverage entries said an operation could not be driven because “this driver’s k() takes one input” — a fact about the harness, not about any backend, whose emitted kernels have taken three buffers all along. Giving the four drivers a second input buffer closed all seven. It also turned this up.

Cambricon emits one #define TILE_SIZE_<K> per kernel, set from the first tile it sees, and sizes every __memcpy by it. For a matmul that is m*k:

8x16x4:  reads  128 floats from p1, which holds k*n = 64   → 64 past the end
         writes 128 floats to   p2, which holds m*n = 32   → 96 past the end

It reads NRAM that was never filled and overflows the output buffer. The emitter’s own module header has said since it was written that a load copies R*C; only equal-sized operands made per_task look like the same number.

The shape of the defect names the one case that hides it: it is invisible exactly when m*k == k*n == m*n — which for a matmul means m == k == n. The square case is the one a hand-written test reaches for first. 4x4x4 passed while 8x16x4 was off by 1.0, 16x8x32 by 1.5e27, and 3x129x5 wrote nothing at all because it had already smashed the heap.

Predicted from reading the emitted C, then confirmed by choosing shapes to test the prediction: 5×5×5 and 8×8×8 pass, 4×4×8 gives 3.2e31, 2×6×3 produces no output. And the fix is checked the same way — where sizes already agree nothing changes: every golden file is byte-identical and the equal-sized shapes return the same values as before. That is what separates a fix from a rewrite.

An emitted kernel that could not run at all

nisa.tensor_reduce takes the operation as its first positional parameter. Eleven of the Neuron emitter’s twelve call sites do that; so does the mapping table in its own module header, and so do its own tests. The rms_norm arm alone passed the data first with the operation as op=, which binds that parameter twice:

TypeError: tensor_reduce() got multiple values for argument 'op'

Raised before the kernel computes anything — on this shim and on real Neuron alike. The origin is next door. nisa.tensor_tensor does take its operands first and the operation as op=, and this file has a dozen such calls. Two neighbouring APIs with opposite conventions, and this arm borrowed the wrong one.

Nothing caught it because emitted text is valid text either way. It surfaced only on widening the Neuron gate to drive rms_norm. And the corrected call does not merely run: it agrees with the reference — a wrong guess at the argument order would have executed and disagreed, so the numbers confirm the direction of the fix, not just its syntax.

“30 refused” was telling us something for months

Every emulator prints a refusal count. emulate_gpu: 20 kernels run, 30 refused — the line as it read when this was found — was saying that six of its ten listed operations are not lowered by the CUDA backend at all — a third of the list has never produced a kernel. The number was there all along; nothing turned it into a claim anyone had to agree with.

All 100 backend–operation pairs are now stated in three categories and every one is checked by emitting:

Driven         must emit AND be named by that emulator's source   87
LoweredButNot  must emit, must NOT be named, reason is a property   5
NotLowered     must FAIL to emit                                   48

The match is exhaustive per backend, so a new operation cannot compile until someone has decided what all five do with it. NotLowered going red is the useful direction: a backend gained an arm and nothing is checking what that arm computes. The seven held back are held back for properties — gpu’s softmax and rms_norm lower to __shfl_down_sync, and one thread cannot be a warp.

Checked in all three directions before being trusted, and the first version failed one. Declaring msl/Matvec not-lowered was caught. Declaring gpu/Softmax driven was not — emission alone cannot separate the two categories, since both require the backend to emit, so marking everything driven passed. A gate that only fails in the direction you thought to test is half a gate.

A false alarm that looked exactly like the real finding

Seven backends are now checked for what they compute — Cambricon, CUDA, MUSA, Neuron and TPU by emulation, Metal on the GPU itself, and linalg through LLVM’s own JIT — all against one shared reference, so none of them can drift apart.

While adding the fourth, a batched sweep reported that TPU's reduce_max returned the sum: 1.264 where 2.025 was due. That is precisely the defect one of these gates was built to catch, and precisely the shape of the Cambricon finding earlier in this poster. It would have made a good headline.

Reading the emitted code first showed jnp.max(t0, axis=-1, keepdims=True) — correct. Running that one case alone gave 2.025. The sweep had reused a single filename across cases, so a later case read an earlier one's output. Every case in the committed test gets its own path, and the note lives in the test's header rather than in someone's memory.

One backend is deliberately not in this line. The AIE emitter does not produce a small vocabulary over arrays; it produces a dataflow program — fifos, workers, placers, dialect ops. Emulating that means modelling the scheduling, and a shim pretending otherwise would return confident wrong answers. Knowing which things you cannot measure is part of measuring.

Why one emulator reaches the reductions and the other cannot

The distinction below is why the shimmed backends do not all reach the same set. It was first drawn between Cambricon, CUDA and AWS Neuron, and it is the reason emulator_coverage.rs now records a property for every operation an emulator cannot drive — all against the single shared reference, so none can drift apart.

The Neuron emulator reaches the reductions and the CUDA one does not, and the reason is a property rather than an accident:

NKI:   nisa.tensor_reduce(np.add, t, axis=(1,))   ← the operation is NAMED
CUDA:  __shfl_down_sync(...) across 32 lanes      ← hand-rolled out of warp shuffles

A named operation can be emulated honestly. A warp cannot be faked one thread at a time — a stub returning the value unchanged would produce a confident wrong answer — so the CUDA gate skips those and this one does not. It is the same property that makes the MLIR backends checkable without a toolchain, turning up somewhere else entirely.

Three harness details live in the test because each would otherwise cost an afternoon: the interpreter is probed, since the default python3 here has no numpy while /usr/bin/python3 does; nl.store(p1[mgrid], v) hands the store a sliced view that numpy copies, silently losing the write; and the reduction must keep dims and accept both a ufunc and a dispatcher, because the emitted code uses both spellings.

From “is it a program?” to “is it the right answer?”

Almost every gate here asks whether emitted text is a program. Only one backend was ever asked what it computes — and that question found all four of its row operations reducing the whole tile instead of each row.

The CUDA backend emits ordinary C once __global__, threadIdx and the math intrinsics are defined, so the same lever works. Its emitted kernels now run against the same reference the Metal and Vulkan paths use: 20 kernels compared across five shapes, zero disagreements.

What it does not cover is in the test, not left to be discovered. The reductions lower to __shfl_down_sync across 32 lanes; one thread at a time cannot make a warp, and a stub returning the value unchanged would compute a confident wrong answer rather than fail. They are skipped, not faked.

The emulator's own first bug is the one worth keeping. The driver linked the kernel instead of including it — and threadIdx is static in the header, so the two translation units got two copies: the driver set its own and the kernel read another. Element 0 of each block came out correct and every other element stayed 0.0. That reads like a partly-working kernel, not a broken harness, which is exactly why it is worth writing down.

Three runs to read one error, because the directory really was there

Codifying the cross-backend sweep produced a failure that resisted the obvious reading: the test died on write: NotFound while printing that the directory it was writing into existed. A probe confirmed the directory was present at every iteration.

The extraction took everything between "__tile_ and the next quote — which also captures literals like "__tile_rms_norm_*: an eps operand is given but …". That is an error message that happens to begin with an intrinsic name. It yields a "name" containing spaces and a slash, and the slash turns dir.join(name) into a path whose parent does not exist. The directory was there; the file's parent was not.

The shared extraction now encodes three rules, each of which cost a wrong answer earlier: skip the emitter's own test module, skip prefix literals ending in _, and a name is identifier characters and nothing else. Two non-obvious exclusions are written into the test itself — SPIR-V output must go to a .comp file because the validator infers the shader stage from the extension, and the two MLIR-emitting backends are excluded because their SSA values are spelled %t0.

The seventh backend — and the guard that is wrong for two of them

A prefix is not a name

Asking the same question of the other emitters produced a suspicious result: hexagon, ttmetal and csl each appeared to lower exactly seven undeclared intrinsics. Identical counts are worth a second look. The seven were:

Three grades of one defect, and the difference is the point

An unchecked index turned up in three places, and what makes them worth separating is that each admits a different answer — the cheapest one available:

slice offset, extent and source size are all compile-time constants → refuse at emit, zero runtime cost
embedding runtime index, constant bound in hand → guard in the kernel
scatter / gather runtime index, bound absent from the signature → filed, because guarding needs a buffer binding across nine emitters and their hosts

All three were reported by the compiler as a field carried into a struct and never read. Proved both ways for the slice: 64 rows at offset 8 of a 256-row source still emits; the same slice at offset 200 is refused with “reads past a 256×256 source — up to row 263”.

Five warnings are left, and all five are findings. The four field `m` is never read are the standing evidence for the scatter issue and must not be silenced with an underscore — they should disappear when the bound is threaded through and read, and not before. That instruction is written into the issue itself, so the next person does not tidy the evidence away.

The bound was carried into the function and thrown away

The Gaudi embedding op receives vocab_size and destructures it as:

vocab_size: _,        // brought in, and explicitly discarded

Meanwhile int _tok = (int)indices[_ei]; indexed the weight table with no check at all. An out-of-range token is an out-of-bounds read.

Fixed here rather than filed — and the distinction is the whole point. Scatter and gather could not be guarded without adding a buffer binding across nine emitters and their hosts. This bound was already in hand as a compile-time constant, sitting beside count and embed_dim in the same struct. Out-of-range tokens now read as zero, which is what an embedding of an invalid token should be rather than whatever was in memory.

And one thing worth knowing about warnings. Cargo prints “generated N warnings” and shows only some. Clearing the visible ones uncovered a further set underneath — including this bound. Getting to zero is not tidiness; it is the only state in which the next one is visible at all. Six findings in this poster arrived through that door.

Scatter writes at an index nobody checks — and the bound is already passed

__tile_scatter_f32 and __tile_gather_f32 take an index array of arbitrary runtime u32, and none of the nine backends that lower them bounds-check it. The Metal body is representative:

uint idx = (uint)p1[gid / stride];
p2[idx * stride + col] = p0[gid];      // scatter: unchecked WRITE
p2[gid] = p0[idx * stride + col];      // gather:  unchecked READ

On a GPU an out-of-range index there is an out-of-bounds device write — not a wrong answer.

The parameter that would bound it is already being passed, and read by nobody. The declaration gives (dst, src, indices, n, m, d), and the safe wrapper says what the declaration doesn't: tile_scatter_f32<N, M, D>(src: Tile<N, D>, ..) -> Tile<M, D>. The destination is M×D, so m is exactly the bound. aie and gaudi carry it in their op structs and never read it; gpu writes let _m = ….

And the repo already knows the pattern — __tile_topk_mask_scatter_f32's own doc reads “if 0<=idx<dst_len”. That one checks. The general scatter does not.

Filed, not fixed, for a stated reason: the Metal kernel's parameters are num_elements and stride, so m is not in the signature. The guard cannot be written without adding a buffer binding, across nine emitters and the hosts that bind them. That is a decision, not a patch.

A grouped-query attention kernel that does not group

__tile_attention_gqa_* is lowered by five emitters and declared by none. It is not in tile_std, which declares the other 423 intrinsics, and appears in no file outside the emitters. So each one documents the signature for itself — and two of them disagree:

nki / tpu   (dst, q, k, v, heads,     head_dim,     seq_len, kv_heads)
gpu         (dst, q, k, v, num_heads, num_kv_heads, seq_len, head_dim)

Positions 5, 6 and 8 mean different things in the two readings. One of them is building kernels from the wrong operands, and nothing in the tree says which.

Separately: nki and tpu do not implement the grouping at all. nki resolved kv_heads and never read it; tpu wrote let _kv_heads = …, which silences the compiler rather than answering it. Both then emitted ordinary attention over every query head — while the nki arm's own comment reads “Decomposed into: for each group, …”. There is no grouping below it.

Both now refuse when kv_heads != heads, and still emit where they are equal, since that is ordinary multi-head attention and the existing lowering is correct for it. Their unit tests had been asserting on the ungrouped output with heads=8 and kv_heads=2 — checking that a transpose and a matmul appear, which they did, in a kernel that ignored the grouping entirely. The answer was one level up: the safe wrappers say which operand is a tile

That part was inferred from parameter names, and the inference was a guess. The emitter knows — but reading the answer out of the emitter and then testing the emitter with it proves nothing.

tile_std answers it without the circularity. It does not only declare the intrinsics, it wraps most of them in typed Rust, and the wrapper call sites state exactly what the declarations omit:

__tile_matvec_f16_bias(0, a.buf_id, w.buf_id, bias.buf_id, N as u32, K as u32)

.buf_id is a tile, X as u32 is a dimension, dst is a literal 0. Written by the safe API's author, not an emitter's — a contract being read, not reconstructed.

The “measured” level recommended a width without checking the answer

-O4 sweeps threadgroup widths on the real device, picks the fastest, and writes it into the emitted source as a dispatch recommendation — a comment the host code is written from. It never read the output buffer. The harness’s sweep mode times each width and exit(0)s before printing a value, so the ranking was on speed alone.

That is the wrong test for this axis. Threadgroup width is the parameter every reduction here folds across, and the power-of-two tree fold produced wrong answers at thread counts that were not powers of two. A sweep that only times would have found such a width fastest and put it in the artifact.

Each candidate is re-run through the ordinary verified comparison at its own width now. A width that disagrees is dropped with its reason; if none survive, no width is recommended at all — a fast configuration that computes the wrong answer is worth less than no recommendation. An op with no reference qualifies the ranking rather than removing it: still ranked, with a note that the ranking rests on timing alone.

It dropped nothing at first — the sweep’s candidates were all powers of two and the fold bug needed a count that was not, so the guard could never have had a width to drop. That is a weak place to leave a safety check, so the candidate list now includes the multiples of the SIMD group between the powers of two: 96, 192, 384, 768. Real tuning space — on an M1 Ultra 384 and 768 measure within 10% of the best.

An f16 sweep: 29 of 108, then 81

Row indexing had never been tested, in any kernel, ever

The reference was handed the same flattened shape, so both sides computed one 387-wide softmax and agreed. The three-way comparison cannot see this — it is not a disagreement, it is two right answers to a question the MLIR never asked.

A multi-hop route degrades honestly: the hardware name comes from the last hop, but the evidence is recorded-here only if EVERY validated hop is. And an evidence pointer must name a file that exists — a test opens every one, because a pointer that cannot be followed is worse than no pointer: it looks checkable. That test failed on its first run, on a path this very change had got wrong.

The blocked fix was the optimal one, not the only one

Two backends were filed unfixable here, on reasoning that was sound: no Cambricon or Habana hardware, and this repo has twice rejected writing plausible kernels it cannot run. Both are fixed now, without acquiring anything.

bang had three defects and #014 said they had to be fixed in one edit or the result would be “differently wrong and look fixed”. The fix is not the MLU cross-task reduction the issue assumed was needed. A row that fits in NRAM does not need splitting. Every task reduces the whole row and task 0 stores — correct at any taskDim, no cross-task communication, all three defects at once. It duplicates work across tasks: a performance cost, not a correctness one, and the emitted source says so.

gaudi was the elementwise template with a reduce in the middle. The accumulator is hoisted above the loop and the single store moved below it; every call in the new shape is one this emitter already emitted, so nothing was invented for a machine that is not here. Its test checks positions — accumulator before the loop, store after the loop’s advance — because a test looking only for _acc would pass on a kernel that still stored every iteration, which is the bug.

The pattern worth keeping. In both cases the blocked thing was the OPTIMAL fix, and a correct one was available without it. “No hardware to verify a cross-task reduction” is true, and it was allowed to stand for “no fix is possible”, which it never implied. A slower kernel that computes the right answer beats a fast one that does not — and unlike the fast one, it can be verified from here. Still not claimed for either: that it runs. Both route lines print [exact, unvalidated on hardware].

The harness was wrong, and the verdict blamed the kernel

One kernel in the corpus disagreed after the tolerance work: the FOUR-argument rms_norm, 3.70e-1 against a reference sitting 2.98e-8 from torch. By the rule this tool teaches — one magnitude far larger than the others is a defect — that is a broken kernel, and the verdict said so: the KERNEL disagrees with torch, look at the lowering.

The kernel was right. Diffed against its five-argument twin, which agrees, the two emitted files differ in one character run: 1e-6 against 1e-3. rms_eps_from_mlir reads argument index 2 — eps in the five-argument form, the ROW COUNT in the four-argument one, whose constant is 1. Both references computed rsqrt(mean + 1.0).

This is the blind spot of a three-way comparison. Its power comes from two independent references agreeing; when the harness hands both of them the same wrong parameter they still agree, and the only side that is right becomes the outlier. Adding a fourth reference would not help. The epsilon is the one parameter the references are given and the kernel is not — it is baked in at lowering time — so it is now checked for in the emitted source, numerically, and -r says so above the figures when it is missing. All 60 kernels in the corpus agree on Metal now.

A tolerance that is derived rather than chosen

ABS_TOL = 1e-5 judged a 1024-term sum and a relu by the same number. An elementwise op’s error does not grow with anything; a K-term reduction’s does. So matmul, matvec and a wide reduce_sum could not pass — and neither could this tool’s own CPU reference, which is how you know the gate had stopped measuring the kernel.

The issue called this a numerics decision. It is not, once the number stops being chosen: guaranteed = (udtype + γK) · Σ|terms| with γK = Ku/(1−Ku) and u = EPSILON/2 is Wilkinson’s bound — no summation order can exceed it, so a kernel outside it is wrong whatever order it used. That is the property a fitted threshold never has.

The first version of this fix was wrong in the way the tool exists to catch. It used f32’s roundoff for every kernel. The msl f16 matmul errs by 2.18e-2 — correctly, because half * half rounds each product before the f32 accumulator sees it — and the new, tighter gate promoted its verdict from a vague “all three disagree” to a confident “the KERNEL disagrees with torch, look at the lowering”. A tighter tolerance pointing confidently at the wrong place is worse than the loose one it replaced.

And #013 was three constants, not one: RunReport.tolerance was the literal 1e-5, and the exit code was worst > 1e-4 — an order looser, so a kernel could be reported outside tolerance and still exit 0.

The control arm caught a bug in the harness I wrote

The first matmul run on Vulkan did not report a wrong number. It reported “the control arm AGREED: dispatching over different inputs produced identical output across all 4096” — and refused to score the run at all.

The cause was in the harness, not the kernel. KernelAbi::parse_glsl read the push-constant block from {…} on one line. Softmax emits { uint num_elements; } pc; on one line and parsed fine; matmul emits M, N and K on separate lines, so no scalars were found, one wrong value was pushed, N arrived as 0, and the kernel’s loop never executed.

A kernel that writes nothing writes the same nothing whatever it is given. That is precisely what the control arm exists to detect, and the only reason this was a caught bug rather than a silent one: every accuracy figure would have compared an untouched output buffer against itself and agreed.

An unhandled intrinsic emitted a working copy of the wrong thing

The kernel type started at Copy and every recognised intrinsic overwrote it — so an unrecognised one left the default standing and the emitter wrote p1[gid] = p0[gid]. That compiles, xcrun metal accepts it, it ignores every buffer past the first two, and tile reported it as [exact, validated on Apple GPU] with exit 0. Found by emitting a matmul at f16 and f32 and diffing the bodies. Now refused at its root, by asking what the emitter understood rather than what the source said.

The check for that had a hole, and an emitter was sitting in it

Fixing the above raised the question of what the other fifteen emitters do. Six emitted and said nothing — because the detector renames the intrinsic and asks whether the output changed, and mlir_to_gpu writes // TODO: unhandled intrinsic: …. Renaming it did change the output, by one word inside a comment, so the detector concluded the emitter had used it. An emitter that mentions what it is about to drop was invisible to the check written to catch emitters that drop things.

Four emitters wrote MLIR SSA names into target source

mlir_to_gpu emitted p1[goff] = %y; into CUDA — the name of an op it had dropped, in a language with no such syntax. Asked to fix that one, I wrote the general property instead: no SSA name from the input may survive into emitted code. It found three more — nki and tpu leaking into Python, bang into C. All four refuse now.

A slowdown was labelled a speedup

The GPU was correctly measured as slower on a small kernel, and reported as speedup: 0.1x — which skims as a win.

The same matmul reported 5.2×, then 18.6×, then 162×

Same kernel, same machine. Nothing was wrong with the kernel: the device samples barely moved (77.75–78.12 µs) while the CPU reference swung by a factor of ten, because it competes for cores with everything else on the box and the GPU does not. A ratio is only as reproducible as its noisiest side, and nothing said which side that was. The report now prints both spreads and names the one that moved.

A debug build inflated every ratio ~11×

Same matmul, same commit, same machine: 59.7× from a debug build, 5.2× from a release one. Device time identical; the unoptimized reference was eleven times slower. A number from a dev build is not reproducible by anyone running an installed one.

A one-sided NaN was skipped, not reported

if e > worst is false when the error is NaN — so every NaN difference was skipped while the element still counted as compared. A kernel producing NaN where the reference produced a number would have passed with a clean maximum error. Found by running sqrt and log over negative inputs, where both sides legitimately produce NaN and agree.

An empty comparison read as agreement

compare maxed error over what came back, so zero values gave zero error and the verdict said “all three agree”. Every run now includes an arm that must disagree; if it agrees, the harness is broken, not the kernel.

Writing through a symlink

-o link.metal replaced the link’s target — a file the user never named, possibly outside the tree. --force is permission to replace the file that was named.

writeln! issues one syscall per field, so four parallel runs interleaved mid-record and left the attempt store unparseable — permanently, from a transient race. Caught by the concurrency scenario on its first run.

--ui native asked for a window and got a web server

--ui took no value, so native was parsed as an input filename, the HTTP server started, nothing was said, and the command hung.

Shape is not behaviour

The wasm bundle was shipped on a test that checked its magic number, version and export names. A deliberate off-by-one that drops the first matching row leaves all of that intact: the structural test passed on that bundle, a behavioural one failed. Demonstrated, not argued.

An unreachable host is not a disproof — nor a pass

A sleeping laptop failed the whole suite. But skipping quietly would let every host being asleep make the scenario pass having verified nothing — the same shape as a comparison over zero values. It now skips loudly by name and refuses a run that reached none.

The repository root would not build

Adding a crate that declares its own [workspace] without listing it in the root’s exclude broke cargo build at the root — for everyone. No test here could see it: tile_cli is itself excluded and builds in its own workspace, so the root manifest is never exercised. It took a clean clone.

Module-local locks compose across none

Every module keeps its own ENV_LOCK, so a lock in one does not exclude another’s tests. Two of them raced on a TILE_HOME neither owned, and a checksum test reported AlreadyPresent.
