| file | what it is |
|---|---|

**Eight and a half of the ten milestones are built** — M1–M5, M7, M8, M10, and the
unblocked half of M9. `crates/tile_cli` builds on
stable, 966 tests are green, and 62 of 133 specification scenarios are live and executing.

```
cd crates/tile_cli
cargo test                                          # 966 tests + the live spec
cargo test --features stats                         # + the corpus and license crypto
cargo run -- doctor                                 # what machine is this
cargo run -- --list-forms                           # the reader/writer matrix
cargo run -- testdata/forms/softmax.mlir -i         # profile: tile plan, hazards, bounds
cargo run -- testdata/forms/softmax.mlir -t msl -o k.metal   # emit real Metal
cargo run -- install                                # what this platform can be given
cargo run -- -d                                     # MCP over stdio, for agents
cargo run -- testdata/forms/softmax.mlir -u          # serve the view on loopback
cargo run -- testdata/forms/softmax.mlir -t msl -O3 -o k.metal   # ask xcrun metal
TILE_SIMULATE=bare cargo run -- doctor               # the emptiest machine that still runs
```

What remains is blocked on things outside this repository, not on effort:

* **M6** (`.rs` inputs) needs the prebuilt LLVM-linked codegen `.so`, whose per-arch
  release inventory has never been audited — which is why the manifest entries carry a
  placeholder hash and *refuse* rather than downloading something unverifiable.
* **M9's other half** — `-O4` measured autotuning needs real accelerator hardware, and
  building and supervising a `ds4-rs-*` engine needs the sibling repositories. The mapping,
  the search and the rules around `-m` are done and tested; the launcher is not, because a
  supervisor whose failure modes nobody has watched is worse than none.
* **`--ui native`** (eframe) and the **egui-wasm bundle** need a GUI stack and a wasm
  toolchain. The server they would be served from is built and tested.
* **`scripts/install.sh`** is deployed from a private repo — its own header says to edit it
  there. The release workflow publishes the assets it would fetch.

## The four things worth knowing before reading any of it

1. **tile-rs has 1.5 readers and 16 writers.** The pandoc grammar fits; the pandoc
   promise does not. The tool is a fan-out, and `--list-forms` makes the sparse graph
   discoverable so users meet its shape rather than a wall of refusals.
2. **Unmeasured refuses.** Commit `f10513c` made every hardware bound query return an
   error when `measured` is false, because the commit before it had approved arch35
   tilings using arch32 numbers. The CLI is the first user-facing surface for that rule
   and it propagates the refusal rather than printing a plausible number. Params are
   chip-keyed: 950PR and 950DT share `dav-3510` but are different silicon and different
   eval images, so each SKU refuses under its own id and DT also refuses known-missing
   vendor dyn-shape ops.
3. **`tile_cli` is excluded from the root workspace and pins stable.** The root
   `rust-toolchain.toml` pins a frozen nightly that reaches every subdirectory; a CLI
   that must build on six triples cannot inherit it.
4. **Every dependency sits behind a feature, and none of them compiles C.** This repo's
   whole graph is 18 crates and `tile_spec` hand-rolled a Gherkin parser rather than take
   one dependency. The default `tile` binary targets under 15.
